# Архитектура и учебные задачи

Проект демонстрирует связку Django и React без отдельного публичного API-сервера: Django обслуживает HTML, JSON и админку, React управляет переходами и интерфейсом. PostgreSQL и фоновые задачи нужны для полного Docker-стенда; минимальный запуск использует SQLite и память процесса.

## Путь запроса

```text
Браузер → Nginx → Gunicorn → Django → PostgreSQL
                             ↓
                    HTML + initial_payload
                             ↓
                       React Router
                             ↓
                   /api/* → кэш → база

Celery Beat → Redis → Celery worker → обновление матч-хаба
```

HTML содержит `json_script` с начальными данными. React монтируется через `createRoot`; это серверный HTML-каркас с данными, а не React SSR/hydration. При отключённом или не загрузившемся JavaScript остаётся простой серверный вариант. Профиль игрока имеет отдельный Django-маршрут и открывается напрямую; отсутствующий игрок возвращает 404.

## Модель данных

| Модель | Назначение |
| --- | --- |
| `ClubProfile` | Названия клуба, контакты, ссылки, сводные показатели |
| `Player` | Состав, позиция, номер, биография, статистика и slug |
| `Match` | Время, соперник, турнир, статус и счёт |
| `NewsPost` | Новость, анонс, текст и дата публикации |
| `GalleryItem` | Медиа-карточка и категория |
| `Trophy` | Достижение и сезон |

Контент хранит базовое поле и варианты `_ru` / `_en`. При отсутствии перевода применяется предусмотренный fallback. Исторические сведения из демо-снимка не обновляются из внешних спортивных API.

## Кэш

- Payload страницы: 5 минут, ключ включает тип страницы, версию контента и адрес запроса.
- Матч-хаб: 15 минут; Celery Beat обновляет его каждые 10 минут.
- Браузерный payload: 1 минута, общие запросы объединяются; уход одного компонента не отменяет запрос другого.
- Изменения контента инвалидируют серверный кэш **после фиксации транзакции**.

Без `REDIS_URL` используется `LocMemCache`. Он подходит одному локальному процессу. Docker задаёт Redis для общего кэша нескольких Gunicorn workers. При ошибке чтения/записи кэша сервер рассчитывает результат из базы; это не отменяет необходимость работающей базы данных.

## Импорт

`seed_demo` заполняет только полностью пустой проект. `sync_reference_snapshot` обновляет записи по ключам и сохраняет посторонние записи. Флаг `--replace` явно очищает таблицы контента перед загрузкой. Весь импорт выполняется одной транзакцией: ошибка откатывает удаления и уже добавленные строки.

Импорт читает локальный JSON, не выполняет сетевой сбор данных. Изменения через `QuerySet.update()` обходят model signals: после собственной массовой загрузки вызывайте `invalidate_public_payload_cache()` после commit.

## Что разобрать на занятии

1. Проследить один запрос от Django view до JSON и React-компонента.
2. Добавить игрока через админку и сравнить RU/EN поля.
3. Открыть профиль напрямую и через SPA-навигацию.
4. Сравнить первый запрос к базе и повторный запрос из кэша.
5. Смоделировать ошибку импорта и проверить откат транзакции.
6. Сопоставить SQLite-запуск и стек PostgreSQL/Redis/Celery.
7. Изменить фильтр календаря и разобрать чистые функции нормализации матчей.

Загруженные изображения доступны по `/uploads/`; `/media/` — страница новостей и галереи. В Docker файлы отдаёт Nginx из общего тома, при локальном DEBUG-запуске — Django.
